## 1. The main result: the firmware is not a transparent modem

PRD decision 5 was false as written. Verified against
`richonguzman/LoRa_APRS_Tracker` — the tracker acts on its own, with no phone
involved and no flag to switch it off:

| Behaviour | Source |
|---|---|
| Auto-acks messages to its own callsign | `msg_utils.cpp:434,442-443` |
| Replies `"pong, 73!"` to `ping` | `msg_utils.cpp:452` |
| Digipeats when `digipeaterActive` | `msg_utils.cpp:423-431` |
| Keeps its own pending-ack state | `msg_utils.cpp:437-441` |
| Deduplicates over 15 s — its own handling only, never the BLE forward | `check15SegBuffer()`, called at `:421` |
| Retries: 6 attempts at 0/30/60/120/120/120 s plus 30 s expiry, ~8 minutes | `msg_utils.cpp:338-364` |

All of it runs **before** the gate `if (bluetoothActive && bluetoothConnected)`
(`LoRa_APRS_Tracker.cpp:215-219`).

**On TX decision 5 holds**: `ble_utils.cpp:172` sends the host's packet straight
to `LoRa_Utils::sendNewPacket()`, bypassing the firmware's buffer and retry.
Retransmission and msgId stay with the app.

> Two corrections to this section, made after the run. The dedup line originally
> read as if the firmware's 15-second window helped the app; it does not — it
> gates only the firmware's own digipeat/ack/reply decisions, while the BLE
> forward sits outside that block and is unconditional. And the retry ladder was
> written as "30/60/120 s", which understates the real span by about half.

## 2. The channel that does not exist yet: the KISS command byte

Three of five agents found the same opening independently.

`kiss_utils.cpp:74` — `encapsulateKISS(const String& ax25Frame, uint8_t command)`
writes a command byte (`0x0f & command`, line 77), but the only existing call is
`encapsulateKISS(ax25Frame, KissCmd::Data)` (line 169). On decode,
`kiss_utils.cpp:117` tests only `KissCmd::Data` and everything else falls into an
unused passthrough.

So there is an already-framed side channel, today empty. The KISS-sanctioned
codepoint for TNC-specific data is `SetHardware` (0x06). A client that does not
know it ignores it: an upstream PR here is **additive and breaks nobody**.

What would travel through it, in order of value: RSSI/SNR/freqError (measured at
`lora_utils.cpp:234-236,260-261`, consumed on-device at `msg_utils.cpp:414`, and
dropped before the phone); a capability handshake; live LoRa parameters; field
configuration.

> Correction after the run: this section originally read as a plan. Under PRD
> §5.2 it is an upstream ask on its own timeline, and nothing in the app may
> depend on it landing.

## 3. Four verified firmware defects, all upstream-able

**a) The host's TX does not come back.** `station_utils.cpp:256` echoes the
tracker's own transmissions to the phone
(`BLE_Utils::sendToPhone(packet); // send Tx packets to Phone too`), but
`ble_utils.cpp:168-175` does not do the same after `sendNewPacket()`. One line of
C++ would give the app physical proof the packet reached the air.

**b) No listen-before-talk on the BLE path.** The firmware guards its own messages
with `(millis() - lastMsgRxTime) >= 4500 && (millis() - lastTxTime) > 3000`
(`msg_utils.cpp:336`). The BLE path has none of it, and does not even update
`lastTxTime` — written only at `station_utils.cpp:266`, `msg_utils.cpp:331` and
`:375`. So the app can key up while the far end is still transmitting, which is
exactly `ge0rg/aprsdroid#270`.

**c) The TNC2 path costs one BLE notification per byte.** `ble_utils.cpp:201` —
`for (int n = 0; n < frame.length(); n++) txBLE(frame[n]);`, and `txBLE` does
`setValue(1 byte) + notify() + delay(3)`. A 100-character frame is 100
notifications and 300 ms of blocked main loop. The KISS path uses chunks, but with
`delay(200)` each.

**d) The phone receives duplicates the tracker suppresses.**
`LoRa_APRS_Tracker.cpp:221` forwards every packet without passing through
`check15SegBuffer()`.

## 4. Ideas that survived

Numbered as they were that day. Their current status is in the outcome table above.

1. F6 inverted
2. KISS 0x06 sideband
3. Delivery as a five-state machine, each state with distinct physical evidence
4. DTN custody transfer: hearing your own packet returned by a digi suppresses the
   aggressive phase of retry, because the digi's copy is already propagating from
   a better antenna. And the negative — no hearback within a window — means the
   transmission never entered the network, which is a completely different
   operator action.
5. Delayed, jittered ack per callsign pair
6. Airtime instead of a character counter
7. Threads keyed by conversation identity, not callsign
8. Content-addressed store: `getAckRequestNumber()` (`msg_utils.cpp:274-280`)
   counts to 999 and wraps, so the msgId is neither stable nor wide enough to be
   an identity
9. Path inferred from passively heard traffic — every decoded frame carries the
   digipeater list with H-bits
10. The activation as a first-class context
11. The tracker as a mailbox: the firmware persists messages to SPIFFS and the app
    has no way to ask for them
12. A macro row derived from live state rather than configured

## 5. Corrections to the PRD that came out of this run

All applied on the same day.

- **F8**: count UTF-8 bytes, not `String.length`. The APRS limit is 67 **bytes**;
  with Italian accents a naive counter shows green on a message that truncates
  mid-character.
- **F7**: size the dedup window without relying on the firmware.
- **Variable-length msgId**: the firmware generates up to three digits, the spec's
  `{MM}` reply-ack has two.
- **F4/F16/F17**: no retention policy. After the fifth activation the useful list
  is buried.
- **Latency**: the "< 200 ms to the BLE write" target measures the interval the
  operator never perceives. What they perceive is the retry ladder, minutes long.
